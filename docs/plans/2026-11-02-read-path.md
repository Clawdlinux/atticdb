# Read path: where AtticDB loses to SQLite and Redis, and what changed

Owner ask (2026-11-02): find where AtticDB loses on the benchmarks, and fix it with engineering, not tuning.

## Method

`bench/reads.py` (on the #147 bench branch) loads the same real-transcript turns and 20,000 file-ref facts into 3 systems:
- **AtticDB:** `atticdb serve`, compression `auto`, Unix socket, Python client.
- **SQLite:** in process, WAL. An index on `(session, seq)`, a primary key on facts, and an FTS5 trigram table for substring search.
- **Redis:** Unix socket, persistence off. A list per session, a string per fact.

The same seeded reads run against each, interleaved: the newest 20 turns of a session, 1 fact by key, and 1-word or 2-word search returning the newest 10 turns with content.

## Findings

1. **A new connection per request.** The Python client sent `Connection: close`, so every read paid a connect and a server thread spawn. Measured on a 64 MiB store: window p50 0.558 ms fresh against 0.299 ms on keep-alive.
2. **An `open` per request.** `Reader` kept a segment open only within 1 call, and `open` was the top CPU item in a `sample` of a window loop.
3. **Inflate and `pread` per window turn** were the next largest group in the same sample.
4. **Search scanned the whole dictionary**, about 5 ms per word at 427k tokens.
5. **Search replies are large:** a median 551 KB of turn content per query. That is most of what remains.

## Changes

| Change | Where |
|---|---|
| Read keep-alive in the Python client, per thread, reads only. A read on a closed connection is retried once; writes keep fresh connections, so the outcome rule holds | bench branch, `clients/python` |
| Segment read handles opened once and shared | `atticdb-tape` `ReadState` |
| Hot cache of decoded window turns, CRC32C-checked on every hit | `atticdb-core` `hot_cache` |
| Trigram map over the dictionary for candidate tokens | `atticdb-core` `search_index` |
| Search walks the newest 64 records first, not 1,024 | `EngineOptions::search_walk_first` |

## Results

512 MiB of real transcripts, 200,494 turns, 20,000 facts, Apple M4. Both builds use the keep-alive client. Runs are interleaved: before, after, before, after. SQLite and Redis rerun in each.

| p50 / p99 | AtticDB before | AtticDB after | SQLite | Redis |
|---|---|---|---|---|
| Window of 20 | 0.256 to 0.268 / 1.20 to 1.25 ms | 0.135 to 0.137 / 1.14 to 1.29 ms | 0.020 / 0.58 to 0.80 ms | 0.031 to 0.034 / 0.13 ms |
| Fact get | 0.037 to 0.039 / 0.19 to 0.42 ms | 0.021 / 0.22 to 0.26 ms | 0.004 to 0.005 / 0.01 to 0.18 ms | 0.007 / 0.01 ms |
| Search | 12.1 to 12.3 / 27 ms | 2.09 to 2.13 / 15 to 18 ms | 0.49 to 1.05 / 5 to 10 ms | none |
| Server RSS | 129 to 146 MiB | 177 to 178 MiB | in process | in RAM |

The keep-alive client alone, measured earlier on a 64 MiB store: window p50 0.558 ms with a new connection per read, 0.299 ms with 1 kept connection.

From the first run, before any change:
- **Load:** AtticDB 14.5 s, durable. SQLite 97 s. Redis 1.3 s, not durable.
- **Size:** AtticDB 330 MiB on disk. SQLite 1,736 MiB on disk. Redis 568 MiB in RAM.

AtticDB still trails on raw read latency. The gap is now about 7x on windows, 4 to 5x on fact gets and 2 to 4x on search against SQLite, and 3 to 4x against Redis. SQLite reads in process, with no socket or JSON, and Redis holds everything in RAM. What's left is HTTP plus JSON per request, and the reply payload: a median search reply carries 551 KB of turn content.

## Next, in order of measured payoff

1. **Search snippets.** Return a window of text around each match, with full turns on request. A median search reply now carries 551 KB, which also floods the model's context. This changes the API: owner decision.
2. **Serialize responses without `serde_json::Value` trees.** The sample showed tree building and string escaping.
3. **Embedded mode** (#151 phase 4): the engine in process, as SQLite runs, to compare like with like.

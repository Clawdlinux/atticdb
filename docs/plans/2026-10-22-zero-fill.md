# Zero-filled spare segments. Implementation plan

> For agents: one implementer on branch `perf/zero-fill`, TDD, one commit per task. Then a spec review and a quality review before the PR.

**Goal:** cut durable-ack latency at agent concurrency (1 to 4 closed-loop writers) by making each `fdatasync` a data flush only.

**Base:** `main` at `c6ef965`. G1's writer count comes from PR #17 (`G1_WRITERS`).

**Rules:** no new crates, no `unsafe`, no bypassed checks. Tests follow `TESTING.md`. Short sentences, no em dashes, one-line comments. Commits use `git commit -s` with the Copilot trailer. Do not push.

**Commands:** the seven Rust commands from the S4 plan, with sim seeds at 2000.

## Evidence

Segments are preallocated with `fallocate` (`dir.rs:312`). On ext4 that creates unwritten extents. The first write to each block converts it, so every `fdatasync` also commits the journal.

A scratch hack that writes zeros over the preallocated segment gave these numbers (G1, L8s_v3 local NVMe, ext4, medians of 3, same boot, off then on):

| writers | engine p50 | engine p99 | engine turns/s |
|---|---|---|---|
| 1 | 300 → 123 µs | 372 → 153 µs | 13.3k → 31.3k |
| 4 | 376 → 141 µs | 462 → 199 µs | 42.4k → 90.1k |
| 16 | 592 → 440 µs | 1,081 → 1,041 µs | 104k → 104k |

Bare and tape moved the same way, so the cost is in the filesystem, not our code.

The hack filled zeros on the writer thread at each roll. That cost about 50 ms per 64 MiB segment and put p99.9 at 50 ms with 16 writers. So the fill has to run off the writer thread.

PostgreSQL does the same for its WAL. `wal_init_zero` (default on) fills new WAL files with zeros, and the docs advise turning it off on copy-on-write filesystems.

## Design

### D1. One spare, filled in the background

A `SpareWorker` thread keeps at most one complete spare segment in the data directory:

1. Remove a stale `spare.tmp`. Create `spare.tmp` and write `segment_size` zero bytes in 1 MiB chunks.
2. `sync_data`, rename it to `spare.zdb`, then `sync_dir`.

It runs when the writer wakes it: at open, and after each roll consumes the spare.

I am choosing a background thread over zero-filling at roll time because the fill takes about 50 ms per 64 MiB segment.

### D2. A roll takes the spare when it is ready

`DataDir::prepare_segment` (`dir.rs:297-323`) checks for `spare.zdb`.

- **Ready:** rename it to `seg-<id>.zdb`, `sync_dir`, then install the manifest as today. The rename replaces `allocate` + `sync_data`.
- **Not ready:** the current `fallocate` path. Nothing waits on the worker.

A crash between rename and manifest install leaves a `seg-*` file past the manifest. Open already removes those (`dir.rs:194-204`).

### D3. Disk space

The spare holds `segment_size` bytes ahead of need. The worker skips the fill unless `available - segment_size >= floor`, where `floor` is the writer's free-space floor (`writer.rs:391`). The writer's group-space check stays as it is, which slightly over-reserves while a spare exists. A failed fill removes `spare.tmp` and retries at the next wake.

### D4. Open and simulation

- Open removes `spare.tmp` and `spare.zdb`, then wakes the worker. A spare left over from before a crash is never trusted.
- Inline simulation has no worker. `prepare_segment` makes the spare synchronously when none exists, before using it. So sims run the same rename path with small segments. The `SimDisk` crash points cover the fill, the rename, and the manifest install.

### D5. No option

There's no knob for zero-filling. Copy-on-write filesystems (btrfs, ZFS, APFS) gain nothing from it and pay one extra segment write. The README says so. Add an option only if someone asks for one.

## Acceptance

At 1 and 4 writers, engine p50 and p99 drop at least 40% and turns/s rises. At 16 writers, nothing regresses and p99.9 stays under 5 ms.

## Not in this plan

- Recycling old segments. Nothing deletes segments yet.
- Flush pipelining. Reviewed and not pursued, see D77.
- `O_DIRECT`, `io_uring`, `RWF_DSYNC`.

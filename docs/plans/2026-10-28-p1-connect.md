# P1: AtticDB in VS Code with 1 command. Implementation plan

> For agents: 1 implementer per task, run in order. Each task is 1 PR from `main`, built TDD. Before merge it gets a spec review, a code-quality review and a Copilot review.

**Spec:** `docs/design/0004-local-agents-and-objects.md`, Track A (A-home, A-connect). Uber issue #71. Research behind task 3: `docs/design/0005`, issue #87.

**Goal:** after `atticdb connect vscode`, a new Copilot chat in VS Code has AtticDB's tools. It starts with a small block of the user's memory already in context, with 0 tool calls.

**Measured facts this plan relies on (2026-10-28):**
- A read tool call takes 0.14 to 0.34 ms. The cost is the model choosing to call it. So the fast path loads memory once at the start, with no tool call.
- Copilot hooks: files in `~/.copilot/hooks/*.json` (or `$COPILOT_HOME/hooks/`), `"version": 1`. VS Code's Copilot harness and Copilot CLI share them. A `sessionStart` command hook gets JSON on stdin with `cwd`, and may print `{"additionalContext": "..."}`. Use the `bash` field. `exec`/`args` work only in the CLI. Source: docs.github.com/en/copilot/reference/hooks-reference and code.visualstudio.com/docs/agent-customization/hooks.
- VS Code user MCP config: `mcp.json` in the profile, top-level `servers`, stdio entries `{"type": "stdio", "command", "args"}`. VS Code's Copilot harness reads `~/.copilot/mcp-config.json`, so the `copilot` entry is the one its chats use. Copilot's agent host and Copilot CLI start MCP servers in the working folder. VS Code's own launcher starts user `mcp.json` servers in the home folder. It doesn't resolve `${workspaceFolder}` in the user config (microsoft/vscode#245905). It does report MCP roots. Copilot user config: `$COPILOT_HOME/mcp-config.json`, else `~/.copilot/mcp-config.json`, top-level `mcpServers`, entries `{"type": "local", "command", "args", "tools": ["*"]}`.
- Long-context quality drops well before 200K (NoLiMa, RULER). So the injected block stays small: at most 6,000 characters, about 1,500 tokens.

**Rules:**
- No new crates. No new features on existing pins. No `unsafe`.
- Tests follow `TESTING.md`: one scenario per path, extend existing tests before adding new ones, table rows over copies.
- Docs: plain short sentences, no em dashes.
- Commits: `git commit -s`, never a `Co-authored-by` trailer.
- A hook must never block or break a chat. It exits 0 and prints `{}` on any failure.

## Task 1: per-user home (A-home)

With no connection flags, `atticdb mcp` and the shell verbs use a per-user home, created on first use.

- New module `crates/atticdb/src/home.rs`.
  - `dir()`: on macOS, `$HOME/Library/Application Support/atticdb`. On Linux, `$XDG_DATA_HOME/atticdb` when that variable is set, non-empty and absolute, else `$HOME/.local/share/atticdb`. `$HOME` must be set and absolute, else an error.
  - `ensure()`: create the home with mode 0700 (recursive). Check it is owned by the user with no group or other bits. Reuse `listen::owned_dir(dir, 0o077)`, which creates with 0700 and checks. Create `atticdb.json` with tenant `me` through the existing `config::init` when missing. A concurrent creator winning the race (`AlreadyExists`) is fine. Create `data/` the same way as the home. Return the config path, the data directory and the tenant name.
- In `mcp::Adapter::new`: when none of `--url`, `--data-dir`, `--config`, `--token-file`, `--tenant` is given, call `home::ensure()`. Use its config, tenant and data directory. (Changed in task 4: `ATTICDB_TOKEN` no longer skips the home. It is ignored there, with a note.) If any of them is given, behavior is unchanged. This covers `atticdb mcp` and every shell verb, since they share `Adapter::new`.
- Tests, in `crates/atticdb/tests/it/mcp.rs` (extend the existing shell-verb rows if that fits, else 1 new test):
  - Set `HOME` to a temp dir and remove `XDG_DATA_HOME`. Then `atticdb append --content x` and `atticdb recent` with no flags return `x`.
  - The home and `data/` are 0700, `atticdb.json` is 0600, at the platform path from `dir()`.
  - A second run keeps the same `atticdb.json` bytes.
  - On Linux only, `XDG_DATA_HOME` set to another absolute dir puts the home there.
  - Socket paths must fit `sun_path` (104 bytes on macOS). Use the short test root from `support.rs`.
- Docs: in `README.md`'s MCP section and in `crates/atticdb/README.md`, the minimal config becomes `{"command": "atticdb", "args": ["mcp"]}`. Say where the home lives.
- Out of scope: `connect`, `doctor`, hooks, session naming.

## Task 2: `atticdb connect` and `atticdb disconnect` for `vscode` and `copilot`

- `atticdb connect <vscode|copilot>` and `atticdb disconnect <vscode|copilot>`. Any other name exits 2 with usage.
- `connect` calls `home::ensure()` first.
- Targets:
  - `vscode`: macOS `$HOME/Library/Application Support/Code/User/mcp.json`; Linux `$XDG_CONFIG_HOME/Code/User/mcp.json` when set and absolute, else `$HOME/.config/Code/User/mcp.json`. Entry at `servers.atticdb`: `{"type": "stdio", "command": <absolute path of the running binary>, "args": ["mcp", "--agent", "vscode-copilot"]}`. (Changed in task 3: no `--session`. The adapter's session defaults to the repo of the client's first `file://` root. That needs a client that reports roots, as VS Code does. Else it is the repo of its working directory. It is the same rule as the hook. Copilot's agent host and Copilot CLI start the adapter in the working folder.)
  - `copilot`: `$COPILOT_HOME/mcp-config.json` when set and absolute, else `$HOME/.copilot/mcp-config.json`. Entry at `mcpServers.atticdb`: `{"type": "local", "command": <absolute path>, "args": ["mcp", "--agent", "copilot"], "tools": ["*"]}`.
- Writing a target file:
  - A missing file is created, with its parent directories.
  - An existing file must parse as a JSON object. One that doesn't, for example with `//` comments, is left unchanged. Exit 1, name the file and say how to add the entry by hand.
  - If the entry already equals the wanted one, print `atticdb is already connected to <name> (<path>)`. Write nothing, make no backup, exit 0.
  - Else copy the existing file to `<path>.atticdb-backup-<unix seconds>`. Write the new JSON (2-space indent, trailing newline) to a temp file in the same directory. Fsync it and rename it over the target. Print `connected atticdb to <name>: <path> (backup: <backup>)`, or `updated` when an older AtticDB entry was replaced.
  - Every other key and every other server stays. serde_json sorts object keys on write; the message says so once ("keys are now sorted").
  - No token or config path is ever written into a harness file.
- `disconnect` removes only the `atticdb` entry, with the same backup and atomic write. Absent entry: print `atticdb is not connected to <name>`, exit 0. Backups are never restored automatically.
- Tests (temp `HOME`, and `COPILOT_HOME` / `XDG_CONFIG_HOME` removed), as table rows where possible:
  - `connect vscode` on a missing file creates it with the entry. A second run prints "already connected" and leaves the bytes and mtime unchanged.
  - Add another server and another top-level key by hand, then `disconnect vscode`. Only `servers.atticdb` is gone. The other server and key stay, and a backup exists.
  - A file containing a `//` comment: `connect` exits 1 and the file is byte-identical.
  - The same 3 rows for `copilot`.
  - No harness file contains the token from `atticdb.json`.
- Docs: usage text in `main.rs`, a "Connect" section in `README.md` (2 commands), crate README.
- Out of scope: hooks (task 3), `doctor`, other harnesses, `code --add-mcp`.

## Task 3: start every chat with a small memory block (sessionStart hook)

- `atticdb hook session-start`:
  - Reads at most 1 MiB of JSON from stdin, synchronously. Takes `cwd` (string). Anything else is ignored.
  - Repo name: walk up from `cwd` to the first directory with a `.git` entry (file or directory). Take its name, else the name of `cwd`.
  - Uses the home from task 1 through the shell verbs' `Adapter` code, so a stopped server is started.
  - All reads share a 3 s budget from the hook's start. At 4 s it prints `{}` and exits, whatever blocks.
  - Reads `fact_list` for `user/` and for `repo/<repo>/` (limit 50 each). Reads `memory_recent` for session `<repo>` (n 5), 1 read per agent: `vscode-copilot` and `copilot`.
  - Prints 1 line: `{"additionalContext": "<block>"}`. When there is nothing to show, or on any error, prints `{}`. Always exits 0. Errors go to stderr only.
- The block, in this order, with stable formatting so the prompt prefix stays the same between chats:
  ```
  AtticDB memory for repo <repo> (facts under repo/<repo>/; snapshot at chat start; call memory_search or fact_list for more)
  Rules:
  - <key>: <content>
  This repo (<repo>):
  - <key>: <content>
  Recent notes (<repo>):
  - <content>
  ```
  - Omit a section with no entries.
  - Each content is cut to 300 characters on a char boundary, newlines replaced with spaces.
  - The whole block is at most 6,000 characters. When it would pass that, stop at a whole line and end with `(more in atticdb)`.
- `connect <vscode|copilot>` also writes the hook file `atticdb.json` in `$COPILOT_HOME/hooks/` (when set and absolute) or `~/.copilot/hooks/`:
  `{"version": 1, "hooks": {"sessionStart": [{"type": "command", "bash": "'<absolute binary path>' hook session-start", "timeoutSec": 5}]}}`
  - The binary path is single-quoted for the shell, with any `'` escaped.
  - The same rules as task 2 apply: idempotent, backup, atomic write.
  - `disconnect` removes the hook file once neither the VS Code nor the Copilot config has an AtticDB entry.
- Tests:
  - Seed memory through the shell verbs: facts under `user/` and `repo/app/`, and turns in session `app`. Run `atticdb hook session-start` with stdin `{"cwd": "<tmp>/app/src"}` where `<tmp>/app/.git` exists. The output has each fact in key order and the turns oldest first.
  - Seed 100 facts of 300 characters: the block is at most 6,000 characters and ends with `(more in atticdb)`.
  - Rows printing `{}` and exiting 0: stdin not JSON, no `cwd`, and no memory for the repo or `user/`. Also a data directory AtticDB refuses (mode 0755). The last row must finish in under 5 s.
  - `connect vscode` writes the hook file. `disconnect vscode` while the Copilot entry remains keeps it. Disconnecting both removes it.
- Docs: README "Connect" section explains the memory block and its size cap. It says how to turn it off: `disconnect`, or delete the hook file.
- Out of scope: capture on `agentStop` (#72) and compaction hooks. MCP `roots` were out of scope too, but shipped in task 3.

## Task 4: hardening

Fixes from the final review of tasks 1 to 3:
- `connect` refuses to replace an entry with connection flags, whose memory stays in another store. `--force` switches anyway.
- With no connection flags, `ATTICDB_TOKEN` is ignored with a note, so the home's token is used. The hook always uses the home.
- The block's header names the repo. The server instructions point to the block and the key layout.
- New files `connect` writes are 0600. A started server runs in `/`, so it holds no repo folder.
- A relative `unix_socket` in a config is made absolute in the adapter's folder and passed to the started server.
- 1 shared `home::user_home()` for `$HOME`.

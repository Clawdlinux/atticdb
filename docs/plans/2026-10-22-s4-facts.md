## Design, grounded in the current code

### What exists

- The v1 fact codec: `key` (1024 bytes), `content` (4 MiB), `meta` (64 KiB), `agent` (255), `source_refs` (1024 LSNs), `idem_key` (128), `tombstone` (`fact.rs:6-22`, `fact.rs:25-46`). Nothing applies it yet.
- `Kind::Fact = 2` on the tape (`zerodb-tape/src/frame.rs:22`).
- The machine accepts only turn batches, after an optional `TenantCreate` (`machine.rs:63-97`). `install` rejects every other kind as `CorruptIndex` (`machine.rs:243`). A unit test pins that (`machine.rs:350`).
- `Selector::FactKey` exists in the forget codec (`forget.rs:17`). S5 applies it.

### D1. One fact per write. No mixed batches

A fact write is one transaction: an optional `TenantCreate`, then exactly one `Fact` record. Turns and facts never share a batch.

I am choosing one fact per transaction over multi-fact batches because I6 scopes fact retries to `(tenant, fact key)`. A batch with two keys has no single retry scope. The engine also has no mixed batching today: `prepare_inner` requires every record after `TenantCreate` to be a `Turn` of one session (`machine.rs:97`), and turn receipts carry dense seqs that facts do not have. Nothing in the evidence asks for atomic multi-key updates.

The spec rule "the same key twice in one batch is rejected with `InvalidInput`" then holds by construction. Prepare rejects any batch with more than one `Fact` record, any `Fact` next to a `Turn`, and any `Forget` (S5), all with `InvalidInput`. See Q1.

### D2. The fact index

New module `crates/zerodb-core/src/facts.rs`, held in `State` next to `index` and `dedup` (`state.rs:10-15`).

```rust
struct Rev { lsn: u64, deleted: bool }
struct Facts {
    map: BTreeMap<(u32, String), Vec<Rev>>, // (tenant, key) -> revisions, oldest first
    dirty: BTreeSet<(u32, String)>,         // changed since the installed checkpoint
    max_keys: usize,
    history: usize,
}
```

- LSN pointers and a tombstone bit only. No content. The bit lets `fact_get` and `fact_list` skip deleted keys without a tape read. It is not content, so I10 holds: forgotten bytes never sit in the index.
- One global map keyed by `(tenant, key)`. A prefix list is `range((t, prefix)..)` with `take_while` on the same tenant and `starts_with(prefix)`. That is O(log n + visited). A per-tenant map of maps adds a level and buys nothing.
- **Current value.** The newest revision by LSN. If it is a tombstone, the key has no current value. The index never walks back to an older revision for that. S5 adds "or forgotten" to the same rule (I9).
- **Current LSN.** The LSN of the current value, or 0 when there is none: never written, deleted, or (S5) forgotten. `if_lsn` compares against this. So `if_lsn = 0` means "no current value", and a deleted key can be created again with `if_lsn = 0`. I am choosing this over "0 only for never-written keys" because `fact_get` returns not found with no LSN for a deleted key, so a caller could never form the right `if_lsn` without reading history.
- **History per key is capped.** New option `fact_history` (default 16, at least 1). `install` drops the oldest revisions past the cap, with one exception below. `fact_history` returns at most `fact_history` revisions and says `truncated` when older ones existed. The tape keeps every revision. S5 export reads the tape, not the index.
- **Key cap.** New option `max_facts` (default 100,000), global like `max_sessions` (`session.rs:126`). Prepare rejects a write that adds a new key at the cap with `ResourceExhausted("facts")`. Writes to existing keys, deletes included, always pass. A tombstone keeps its slot until compaction exists. Deleting a key that has no revisions still writes a tombstone and takes a slot. That keeps delete one code path and makes it idempotent.
- Memory bound for I12: at most `max_facts` keys of at most 1024 bytes, each with at most `fact_history` plus a few 16-byte revisions. Defaults: about 100 MiB of keys in the worst case, 26 MiB of pointers.

**Reads see the snapshot, never a fallback.** The machine publishes into `State` before the tape stores its durable LSN (`writer.rs:583-593`), and `Tape::read` refuses LSNs above it (`writer.rs:283`). So a reader can see an index revision whose frame is not readable yet. Readers take the state lock, then `durable_lsn`, as `window_snapshot` does (`engine.rs:526`). They use the newest revision at or below that snapshot. A revision above it belongs to a group whose replies have not been sent, so it is not acknowledged yet. Using the value before it is the snapshot read, not the I9 fallback. If the newest revision at or below the snapshot is a tombstone, the key has no value.

For that read to always find the pre-group revision, trimming in `publish` keeps the newest revision below the group's first LSN: drop the oldest while `len > fact_history && revs[1].lsn < group_first`. Replay has no pending group, so it trims to `fact_history` exactly. The extra pointers are bounded by same-key writes in one group and go on the next trim. Responses never show more than `fact_history` revisions, so publish and replay stay visibly identical, as `StateMachine::replay` requires (`state_machine.rs:59-63`).

### D3. `if_lsn` is checked in prepare, by the single writer

- The tape gets one opaque field: `PreparedBatch::application_arg() -> Option<u64>`, set through `append_with_digest(batch, mode, digest, arg)` and `enqueue_sim(records, digest, arg)` (`writer.rs:1040`, `writer.rs:1077`). It is never framed, like `application_digest` (`writer.rs:142`). I am choosing an opaque tape field over encoding `if_lsn` into the record and stripping it in prepare, because the stripped form would be a second, hidden payload format that must never reach disk. The v1 fact payload stays as fixed in S1.
- Prepare order for a fact batch:
  1. Validate: one `Fact` record after an optional `TenantCreate`. The payload decodes. Key is 1 to 1024 bytes. `source_refs` is empty (see Q2). A tombstone has empty content and meta. The payload's `idem_key`, if any, is the retry key.
  2. `state.failure` check, as for turns (`machine.rs:122-124`).
  3. Dedup lookup in the machine overlay, then in published state (`machine.rs:126`). A hit returns `Prepare::Reply` with `REPLY_DEDUPLICATED`. This runs before the `if_lsn` check, so a retry of a committed conditional write gets its receipt, not `Conflict`.
  4. `can_stage` (`machine.rs:133`).
  5. Current LSN: the machine's staged overlay first, then `state.facts`. Mismatch: `Reject` with `Conflict`, `NotCommitted`.
  6. Key cap for a new key, counting keys staged in this group.
  7. Assign LSN and txn. Stage the overlay entry and the dedup entry.
- The staged overlay is `HashMap<(u32, String), Rev>` in `Machine`, like the staged `dedup` (`machine.rs:25`). Two conditional writes to one key in one group then see each other: the second gets `Conflict`. `publish` removes an overlay entry when it installs the record with that LSN, the same way it moves staged dedup entries (`machine.rs:236-240`). A failed sync poisons the writer and the overlay is never read again (`state_machine.rs:42-44`).
- New `ErrorKind::Conflict`. `tape_error` maps it to `Error::Rejected("conflict")`. `EngineError::write` maps `Rejected("conflict")` back, in an arm placed before the catch-all `Rejected(resource) => ResourceExhausted` (`error.rs:36-40`). Without that arm a conflict would surface as 429.
- Outcome: always `not_committed`. HTTP 409 with `"error": "conflict"`, distinct from `"idempotency_conflict"`. The outcome rule is unchanged: after an earlier unclear attempt, a `Conflict` merges to `unknown`, because the first attempt may have committed and moved the current LSN.

### D4. Idempotency reuses the dedup table

- `DedupKey(u32, String, String)` (`dedup.rs:9`) gets a scope enum: `DedupKey(tenant, Scope::Session(name) | Scope::Fact(key), idem_key)`. A session and a fact key with the same name never collide. Per-tenant and global bounds are unchanged.
- Digest: BLAKE3 over `len || payload` of the one fact record, the same shape as turns (`engine.rs:261-268`). `if_lsn` is not part of it. A precondition is not the request's identity, and replay cannot recompute it: `if_lsn` is never on the tape, and replay rebuilds dedup entries from tape records (`machine.rs:219-235`). A retry with the same key and payload but a different `if_lsn` returns the original receipt. Documented.
- Replies: the cached reply is empty, or one `REPLY_DEDUPLICATED` byte. The receipt's `lsn` is `last_lsn` from `Committed::Durable`, which skips a leading `TenantCreate`.
- The caller fast path in `Engine::append` (`engine.rs:270-288`) moves into a shared helper used by turns and facts. It returns a covered published receipt with `deduplicated: true` without the writer.
- After restart: replay rebuilds fact dedup entries from the payload, so I6 holds across reopen within the window.

### D5. Checkpoints and recovery (I8)

- Two new record tags in checkpoint files, next to tags 1 to 3 (`checkpoint.rs:210-262`):
  - tag 4, fact entry: `tenant u32 | key | count u32 | (lsn u64, deleted u8) * count`, newest `fact_history` only;
  - tag 5, fact dedup entry: `tenant u32 | key | idem_key | digest | txn | first_lsn | last_lsn`. No reply bytes.
- Incremental files write `facts.dirty`. Full files (chain of 8, `checkpoint.rs:320`) write every key. A later file's tag 4 replaces the key's entry. The install clears `facts.dirty` the way it clears page dirt (`checkpoint.rs:527`).
- Load checks: tenant registered, count at least 1, LSNs nonzero, strictly increasing and at or below the file boundary. Load trims to the current `fact_history`, so a smaller option does not fail open. Any failure is `corrupt()`, and `load` falls back to a full replay (`checkpoint.rs:278-288`). A checkpoint that disagrees with the recovered tape retries from LSN 0 (`engine.rs:192-224`). Never wrong state.
- The fact index is always resident and capped, so replay needs no spill for it. The session-page spill (`machine.rs:294-312`) is unchanged.
- Old checkpoints have no tags 4 and 5 and load as before. The magics stay `ZCM2` and `ZCK2`.

### D6. Forget readiness, not forget

S4 leaves S5 three hooks and implements none of them:

- `Selector::FactKey` resolves to `facts.map[(tenant, key)]`: all revisions at or below the cutoff.
- The read rule in D2 has one place that picks "the newest revision at or below the snapshot". S5 adds "and not forgotten, else no value". It must never pick an older revision.
- "Current LSN" in D2 already treats "no current value" as 0. S5 adds forgotten to that set in prepare.

### D7. HTTP

Keys go in the JSON body for writes and in the query string for reads, never in the path. Keys contain `/`, so `GET /v1/facts/{key}/history` collides with a key ending in `/history`, and proxies decode `%2F` differently. S3 logging never logs a query string (`docs/plans/2026-10-21-s3-server-mcp.md`, T3 logging), so keys stay out of logs too. Reads reuse `decode` (`api.rs:283`), so `+` means a space and a literal `+` is `%2B`.

| Route | Input | 200 body |
|---|---|---|
| `POST /v1/facts/put` | `{"key", "content", "meta"?, "agent"?, "idem_key", "if_lsn"?}` | `{"outcome": "committed", "deduplicated", "txn", "lsn"}` |
| `POST /v1/facts/delete` | `{"key", "agent"?, "idem_key", "if_lsn"?}` | same |
| `GET /v1/facts/get` | `?key=` | `{"fact": {"key", "lsn", "commit_time_ns", "agent", "content", "meta"}}` or `{"fact": null}` |
| `GET /v1/facts/history` | `?key=&max_bytes=` | `{"revisions": [{"lsn", "commit_time_ns", "agent", "deleted", "content", "meta"}], "truncated"}`, newest first |
| `GET /v1/facts/list` | `?prefix=&after=&limit=&max_bytes=` | `{"facts": [...], "next": <key> or null}`, key order |

- A missing fact is 200 with `"fact": null`, not 404. 404 already means an unknown route, and a client talking to an S3 server must not read "route missing" as "fact missing".
- Limits: `key` 1 to 1024 bytes. `content` a UTF-8 string up to 4 MiB. `meta` a JSON object up to 64 KiB. `agent` up to 255 bytes, default empty. `idem_key` 1 to 128 bytes, required. `if_lsn` an unsigned integer. `prefix` and `after` up to 1024 bytes. `limit` default 100, max 1,000. `max_bytes` default 1 MiB, max 8 MiB.
- Budgets: the first fact or revision is always returned, so a cursor always advances. Later ones stop before the budget is passed. `next` is the last returned key when more may follow. A list visits at most 1,024 index entries per call, tombstones included, so a prefix full of deletes costs O(1,024), not O(keys). Tape reads are one per returned fact.
- `prefix` is a byte prefix. `repo/pay` matches `repo/payments/...`. Docs say to end a prefix with `/` for path semantics.
- Write response table: S3's table (`api.rs:164-210`) plus two rows. Everything else, the outcome rule and the committed-without-receipt row included, is unchanged.

  | Engine result | Status | Body |
  |---|---|---|
  | `FactWritten` | 200 | `{"outcome": "committed", "deduplicated", "txn", "lsn"}` |
  | `Conflict` | 409 | `{"outcome": "not_committed", "error": "conflict"}` |

- `ResourceExhausted("facts")` is the existing 429 row with `"resource": "facts"`. The `InvalidInput` message names the fact limits.
- Reads use the window path's `PARSERS` and `SENDING` budgets (`api.rs:85-87`) and its error mapping.

### D8. MCP tools

Three tools, as the spec lists. The model never sees idempotency keys, tokens, tenants or `if_lsn`.

- `fact_set {key, content?, delete?, meta?}`. Exactly one of `content` or `delete: true`. Description: "Save a rule or fact under a path-like key, for example repo/payments/api/retry-rule. It replaces the key's current value, so a correction supersedes the old rule. Pass delete: true to remove the key. Every agent using this memory shares the same keys." Returns `committed lsn=<n>` and `structuredContent {committed, lsn, deduplicated}`.
- `fact_get {key}`. Description: "Read the current value of one key. A deleted key returns nothing, never an older value." Returns the content as text, or "no current value".
- `fact_list {prefix, after?, limit? = 50 (max 200), max_bytes? = 64 KiB}`. Description: "List current facts whose keys start with prefix, in key order, with their content. Call it before working in an area, for example with prefix repo/payments/." Text is one `key: content` block per fact, then `more: call again with after=<key>` when `next` is set.
- `agent` comes from `--agent`, as for `memory_append`.
- No `if_lsn` in v0.1. The model holds no reliable LSN in context, and a stale one turns every correction into a `Conflict` loop. The single writer already orders writes. The later write wins, which is what "a correction supersedes the old rule" means. Programs that need compare-and-set use HTTP or the Python client.
- One `idem_key` per tool call, retried through the shared `retry` and `Merge` (`mcp.rs:227`, `outcome.rs`).

### D9. Python client

`fact_put(key, content, meta=None, agent=None, if_lsn=None, idem_key=None, resume=None)`, `fact_delete(key, agent=None, if_lsn=None, idem_key=None, resume=None)`, `fact_get(key)`, `fact_history(key, max_bytes=None)`, `fact_list(prefix="", after=None, limit=None, max_bytes=None)`.

- The retry loop in `append` (`zerodb_client.py:117-151`) moves into one private `_write(target, body, key, resume)`. All three writes use it. Same deadline, the same 2 s reserve, the same merge.
- New `Conflict(NotCommitted)`. Raised only when the merged state is `not_committed` and the last reply's `error` is `conflict`. After an unclear attempt the call raises `OutcomeUnknown`, never `Conflict`.

## D76 text

Under "Slim v0.1 (0003)", after D75:

```markdown
| D76 | S4 facts. One fact per transaction, after an optional `TenantCreate`. Facts never share a batch with turns. The fact index is one `BTreeMap` from `(tenant, key)` to LSN pointers with tombstone bits, capped by `max_facts` (default 100,000, global) and `fact_history` (default 16 per key), checkpointed as tags 4 and 5. The current value is the newest revision by LSN, and a tombstone means none. The current LSN is 0 when there is no current value. `if_lsn` reaches prepare through an opaque, unframed `PreparedBatch::application_arg`, and is checked after the retry lookup against the staged overlay and then the published index. A mismatch is `Conflict`, `not_committed`, HTTP 409 `conflict`. Retries reuse the dedup table with a session or fact scope. The digest covers the payload only. Reads pick the newest revision at or below the durable LSN they observed. HTTP keeps keys out of paths. MCP exposes `fact_set`, `fact_get` and `fact_list`, without `if_lsn`. No new dependencies | One key per write keeps I6's `(tenant, key)` scope. Replay cannot recompute a digest that covers `if_lsn`, which is never on the tape. A stripped in-band condition would be a hidden payload format. The machine publishes before the tape stores its durable LSN, so a reader must not trust the newest index entry alone. Keys hold `/`, which collides with path suffixes and proxy decoding |
```

## Risks

| Risk | What could go wrong | Mitigation in this plan |
|---|---|---|
| A stale value comes back | A read or a crash shows a superseded or deleted value (I9) | No read path walks history for a value. Engine sim oracle on every seed, `PublishPause` row, process-level SIGKILL row |
| Snapshot gap | A reader sees an index revision whose frame is not durable yet and fails, or returns "no value" | Snapshot rule and pre-group trimming (D2). Tested by the `PublishPause` row |
| `Conflict` hides a commit | A retry after `unknown` gets `Conflict` because the first attempt moved the current LSN, and the client reports nothing written | Retry lookup runs before the `if_lsn` check. Past the dedup window the outcome rule keeps `unknown`. Python raises `Conflict` only from a clean `not_committed` |
| `Conflict` read as 429 | `Rejected("conflict")` falls into the catch-all `ResourceExhausted` arm (`error.rs:40`) | Explicit arm before it. `api::facts_over_http` asserts 409 `conflict` |
| Two 409s | Callers mix up `conflict` and `idempotency_conflict` | Distinct `error` names and Python exception types. Both documented |
| History looks lost | `fact_history` shows 16 revisions while users expect all | `truncated: true`. The tape keeps every revision. S5 export reads the tape |
| Tombstones fill the cap | Deletes never free slots, so a churny tenant hits `ResourceExhausted("facts")` | Documented. Compaction is a deferred non-goal with its own unblock evidence. The cap is configurable |
| One tenant takes the global cap | Like `max_sessions`, `max_facts` is global | Same posture as sessions. See Q3 |
| Full snapshot lock hold | A full checkpoint copies the whole index under the state lock | Measured in T3 at 100,000 keys. `Arc<[Rev]>` if over 10 ms |
| Tombstone-heavy prefixes | Pages come back short | Visit budget of 1,024 per call and an `after` cursor. Cost stays bounded |
| `+` in keys over HTTP | A raw `+` decodes to a space | Documented. The Python client and MCP adapter percent-encode. Tested in `api::facts_over_http` |

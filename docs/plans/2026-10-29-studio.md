# Studio: see what is in zerodb. Implementation plan

> For agents: 1 implementer per task, run in order. Each task is 1 PR from `main`, built TDD. Before merge it gets a spec review, a code-quality review and a Copilot review.

**Goal:** `zerodb studio` opens a local, read-only web page that shows what is in the store. You see the newest records, every session's turns, every fact with its history, search, store health, and the exact memory block an agent gets at chat start.

**Why a web page and not a TUI or a REPL:**
- Memory is long text. A browser wraps it, highlights search words, and draws charts. A terminal does none of that well.
- A TUI needs new crates (ratatui, crossterm). The no-new-crates rule rules that out.
- zerodb has no query language, so a psql-style REPL would only wrap the shell verbs. They already print 1 JSON line each.
- The pattern is common for local data tools: Prisma Studio (`npx prisma studio`), Datasette (`datasette serve`) and Jupyter all serve a page on loopback and open the browser.

**Facts this plan relies on (2026-10-29):**
- The home store today: 32 records, 14 facts (11 under `repo/zerodb/`, 3 under `user/prefs/`), 15 fact revisions, 1 tenant. A month of daily use may reach a few thousand turns and a few hundred facts. The engine caps sessions at 1,000,000.
- The home server listens on a Unix socket only. Browsers cannot reach a Unix socket, so the studio is a small HTTP bridge in front of it.
- No list-sessions API exists. No "newest records" API exists; `search` needs words.
- Jupyter opens the browser through a 0600 redirect file, so its token never shows in a process argument (`use_redirect_file` in `jupyter_server/serverapp.py`). On macOS and default Linux, any local user can read other users' process arguments.
- zerodb makes no outbound network calls (`docs/design/0004`). So the page loads no fonts, scripts or styles from the web.

**Rules:**
- No new crates. No new features on existing pins. No `unsafe`.
- Tests follow `TESTING.md`: one scenario per path, extend existing tests before adding new ones, table rows over copies.
- Docs: plain short sentences, no em dashes.
- Commits: `git commit -s`, never a `Co-authored-by` trailer.
- The studio never writes to the store. It has no code path that sends a write route.

## Task 1: 2 read routes, `GET /v1/sessions` and `GET /v1/records`

Both are tenant-scoped, need the token, and work on TCP and the Unix socket like `GET /v1/window`.

**`GET /v1/sessions?limit=&after_agent=&after_session=`**
- Lists the tenant's sessions that have at least 1 published turn, in byte order of `(agent, session)`.
- `limit`: default 100, at most 1,000 (`MAX_WINDOW_TURNS`), at least 1.
- `after_agent` and `after_session`: an exclusive cursor, both or neither. One without the other is 400 `invalid_input`.
- 200: `{"sessions": [{"agent", "session", "turns"}], "next": {"agent", "session"} | null, "total": {"sessions", "turns"}}`. `total` counts all the tenant's sessions and turns, not only this page.
- Engine: `Engine::sessions(tenant, SessionQuery { after, limit }) -> Result<SessionPage>`. 1 pass over the session index under the state lock: O(sessions) time, O(limit) memory. Keep the `limit` smallest keys above the cursor in a bounded max-heap. Do not clone or sort every key.
- `turns` is the published length. A session with only reserved, unpublished turns is skipped.
- An unknown tenant gets an empty page with zero totals.
- Measure 1 call over 100,000 sessions in release mode. Put the number in the doc comment.

**`GET /v1/records?before=&limit=&kind=&max_bytes=`**
- The tenant's turns and fact revisions, newest first by LSN, each as written. A fact delete shows with `"deleted": true` and empty content. Superseded revisions show too. It is the log, not the current state.
- `before`: exclusive LSN cursor, a previous page's `next`. `limit`: default 50, 1 to 1,000. `kind`: `turn` or `fact`, optional. `max_bytes`: default 1 MiB, at most 8 MiB. The first record is always returned.
- Visits at most `SEARCH_VISITS` records per call. `next` resumes below them. `next` is null once the walk reached LSN 1.
- 200: `{"records": [...], "next": <lsn> | null}`. A turn: `{"kind": "turn", "lsn", "commit_time_ns", "agent", "session", "seq", "role", "content", "meta"}`. A fact: `{"kind": "fact", "lsn", "commit_time_ns", "key", "agent", "deleted", "content", "meta"}`. Content and meta go through the existing `blobs()` rule.
- Engine: `Engine::records(tenant, RecordQuery { before, limit, kind, max_bytes, visits }) -> Result<RecordPage>`. Share the newest-first walk with `search` through 1 private helper, so the two cannot drift. Read at the same durable snapshot `search` uses.
- Forgets are not applied by the engine yet. When they are, `records` must hide what `window` and `search` hide.

**Both:**
- Add `Route::Sessions` and `Route::Records` to `api.rs` and `serve.rs`. Unknown query parameters are 400, as in the other read routes.
- No MCP tools and no shell verbs for these. The studio is their only caller for now.
- Tests:
  - Engine, 1 scenario: 2 tenants, 3 sessions in tenant A across 2 agents, facts put, updated and deleted. `sessions` pages in order with a cursor, totals match, tenant B sees none of A. `records` is newest first, `kind` filters, the delete and the superseded revision show, `before` pages, a small `max_bytes` cuts with `next`.
  - HTTP: extend the existing read-route test with rows: 401 without a token, 400 for `after_agent` alone, 400 for an unknown parameter, 200 shapes for both routes.
- Docs: the route list in the `api.rs` header comment and in `crates/zerodb/README.md`'s HTTP API section.

## Task 2: `zerodb studio`, the bridge server

`zerodb studio [--url ...|--data-dir ...|--config ... --tenant ...|--token-file ...] [--port <n>] [--no-open]`

- Connection flags work as in `zerodb mcp`. With none, it uses the home and starts the home server if needed, through the existing `Adapter` and `Launch` code. Reads fail fast: probe `GET /healthz` once at start, exit 1 with the error if it fails.
- Binds `127.0.0.1:<port>`, port 0 by default. Never another address.
- Makes a 128-bit secret per run with `random_hex(16)`.
- Prints `zerodb studio: http://127.0.0.1:<port>/#k=<secret>` and `Press Ctrl-C to stop.` on stdout.
- Unless `--no-open`: writes a redirect page to `<home>/studio.html` (temp file with mode 0600, then rename), and runs `open <file>` on macOS or `xdg-open <file>` on Linux, detached, with null stdio. The secret never goes in a process argument. A failed open prints a note and keeps serving.
- Serves until killed. 1 thread per connection, at most 16 open. Past that, 503 `busy`. Request bodies are refused (`body_bytes` 0).
- Every request: `Host` must pass `api::loopback_host`, else 403. Only `GET`, else 405.
- Routes:
  - `GET /`, `/app.js`, `/app.css`: embedded with `include_str!` from `crates/zerodb/studio/`. No secret needed; they hold no data.
  - `GET /api/v1/{sessions,records,window,search,facts/list,facts/get,facts/history}`: forwards `GET /v1/<same path>?<same query>` with the tenant token. Returns the store's status and JSON body as they are.
  - `GET /api/v1/stats` and `GET /api/metrics`: forward `/v1/stats` and `/metrics`. Over TCP stores these are refused by the store; pass that through.
  - `GET /api/block?repo=<name>`: `{"repo", "block": <string> | null, "chars", "max": 6000}`. Built by the session-start hook's own code, refactored to take a repo name, so the preview cannot drift from what agents get.
  - `GET /api/info`: `{"version", "tenant", "store": "home" | "data_dir" | "url", "home": <path> | null}`.
  - Anything else is 404. `/api/*` needs header `X-Zerodb-Studio: <secret>`, compared in constant time, else 401.
- Every response carries:
  - `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`
  - `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `Cross-Origin-Resource-Policy: same-origin`.
  - The store server's responses stay byte-identical. Add extra headers to `http::Response` in a way that leaves them empty there.
- Never logs a query string, a header value or the secret. 5xx answers log 1 stderr line, as `serve` does.
- Each forwarded call has its own 10 s deadline. The tenant token never reaches the browser.
- Why this shape:
  - Host check: blocks DNS rebinding.
  - Custom header with no CORS answer: a page on another origin cannot send it, so it cannot read memory.
  - Secret in the URL fragment: browsers never send a fragment to the server, so it stays out of logs and `Referer`.
  - 0600 redirect file: the secret stays out of `ps`.
- `crates/zerodb/studio/index.html` in this task is a plain page that calls `/api/info` and shows the result. Task 3 replaces it.
- Tests, in `crates/zerodb/tests/it/studio.rs`, 1 scenario with rows. Seed a temp home through the shell verbs, start `zerodb studio --no-open`, read the port from stdout:
  - `/` is 200 `text/html` with the CSP header. `/app.js` is `text/javascript`.
  - `/api/v1/sessions`: 401 with no header and with a wrong secret, 200 with the right one, and the body matches the store's.
  - `Host: evil.example` is 403. `POST /api/v1/sessions` is 405. `/api/v1/append` and `/api/v1/facts/put` are 404.
  - `/api/block?repo=app` returns the same block as `zerodb hook session-start` for that repo.
  - The tenant token appears in no response.
  - `--no-open` writes no `studio.html`.
- Docs: usage text in `main.rs`, a "Studio" section in `README.md` and `crates/zerodb/README.md`, decision D87 in `docs/design/0002-decision-log.md`.

## Task 3: the page

Static `index.html`, `app.css` and `app.js` in `crates/zerodb/studio/`. Vanilla JS, no build step, no framework, no web fonts. Hash routes, so reload and back work.

**Safety rules for `app.js`:**
- Memory content is untrusted text. Render it with `textContent` and `createElement` only. `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write` and `eval` must not appear in the file. A test greps for them.
- No inline `style=` attributes or inline scripts: the CSP blocks them. Use classes, or CSSOM properties set from JS.
- On load, read `#k=` from the URL, store it in `localStorage`, and remove it from the address bar with `history.replaceState`. Send it as `X-Zerodb-Studio` on every `/api/` call. A 401 shows: "This link is out of date. Open the link `zerodb studio` printed."
- `commit_time_ns` passes 2^53, so JS reads it as a rounded double. Use it for display only, never send it back.

**Design (design-taste-frontend, app screen):**
- Style dealt: `achromatic-ledger`, seed 111301075, kind `devtools`, light. Ink chrome, 1 chart hue `#1d5fbf` on the main data element, figures in mono.
- Why: you open it for a quick look a few times a day, mostly to read text. zerodb is an append-only log where every record has an LSN, so the ledger move fits.
- Face: a blue-grey ground `#f2f4f7`, as for a ledger. Every LSN, count and time in the system mono stack, as a ledger's columns. System fonts only, as zerodb makes no outbound calls.
- Signature element: the chat-start block, shown as the agent will get it, with its size on a bar against the 6,000-character cap.
- Data inventory:
  - Records: LSN, time, agent, session or key, role, content, meta.
  - Facts: key, content, agent, LSN, time, revisions.
  - Sessions: agent, session, turns.
  - Health: health, durable LSN, facts, revisions, writer stage times, ack latency histogram, index residency.
  - People: 1 developer, a few quick looks a day on a laptop.
  - Jobs, most frequent first: check what agents saved, preview the next chat-start block, find a note, read a fact's history, check health.

**Screens** (h1 is a noun; each has 1 question):
1. **Overview** `#/`: "What did my agents save lately?" The finding line under the title names the newest write: time, agent, session or key. If an agent saved nothing today, it says so. Blocks: the 8 newest records; the chat-start block for the newest repo; 1 store line with health, durable LSN, facts, sessions and turns.
2. **Log** `#/log`: all records, newest first. Tabs: All, Turns, Facts. "Older" pages with `next`.
3. **Sessions** `#/sessions`: agent, session and turns, with a filter box. Session `#/session/<agent>/<session>`: turns newest first, "Older" pages with `since_seq`.
4. **Facts** `#/facts`: keys grouped by prefix (`user/`, `repo/<repo>/`). Fact `#/fact/<key>`: current value and every revision, deletes marked.
5. **Search** `#/search?q=`: hits newest first, matched words highlighted with text nodes, "Older" with `next`.
6. **Chat start** `#/chat-start?repo=`: a repo picker built from `repo/<repo>/` keys and session names, the block in mono, chars used of 6,000.
7. **Health** `#/health`: KPIs, mean writer stage time per group, the ack latency histogram parsed from `/metrics`, index resident bytes against budget.

- States for every block: empty (fresh home: say how to connect an agent), loading, error (store unreachable: the error and `zerodb serve` hint), 401.
- Phone (390): the sidebar folds into a 48px top bar with a menu.
- `crates/zerodb/studio/seed.sh` seeds a temp home with realistic memory through the shell verbs, for screenshots and manual checks. No lorem, no placeholder names.
- Check, at most 3 rounds:
  - Run `lint.mjs --app` and `inspect.mjs --app` at 1440, 768 and 390.
  - Fix every FAIL. Defend or fix every WARN.
  - Answer the 7 critique questions in writing.
- Tests: the forbidden-API grep for `app.js`. One studio test row loads `/` and checks every asset it links is served.

## Out of scope

- Writes from the page: fact edit, delete, forget.
- Remote access, TLS, multiple users.
- A TUI, a REPL, and new shell verbs for sessions or records.
- Charts beyond the health screen.

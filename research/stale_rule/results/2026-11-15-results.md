# Stale rule or migration: results (2026-11-15)

Claude Code 2.1.310, `claude-sonnet-5-5`, 1 harness. 4 synthetic projects. Not a claim about other agents or real repos.
336 runs completed. 43 failed attempts were excluded and retried.
The CSVs record the exit status, not the cause of those failures.
Final replies were checked locally. The CSVs let you recompute the totals, not verify the replies.
Every run passed the project's tests, wrong choices included. So a wrong choice here is silent.
Cost: $19.14 at API prices, on the eval subscription login.

## The question

A rule says X. The code does Y. If the code moved after the rule, the rule is stale: follow the code.
In these fixtures, a rule added after the code represents an intended migration.
Both cases have byte-identical working trees. The histories differ.

## 1. Rule in CLAUDE.md, 3 reps

| Arm | Stale: follows code | Migration: follows rule | Ran `git log`, `blame`, `show`, or `diff` |
|---|---|---|---|
| plain | 0/12 | 12/12 | 7/24 |
| code-wins, arXiv 2610.30571's sentence | 12/12 | **0/12** | 15/24 |
| history sentence | 12/12 | 12/12 | 24/24 |
| history sentence + provenance line | 12/12 | 12/12 | 18/24 |

- Plain agents follow the file, as the paper found. 11 of 12 said the code disagreed and followed the file anyway.
- The paper's sentence fixes stale rules and breaks every migration. The agent writes the old style into new code. It cites "existing code wins" and offers to switch if you want.
- 1 sentence about history gets both right: "A rule changed after the code it describes is the new direction. Code changed after the rule means the rule is stale."

## 2. Rule from a memory hook, refactor commits say what changed, 3 reps

The repo never holds the rule. A test hook simulates AtticDB's SessionStart block.
The stale history's refactor commit says what it did, such as "refactor: lookups return None for a missing item".

| Arm | Stale | Migration |
|---|---|---|
| plain, undated | 12/12 | 12/12 |
| code-wins | 12/12 | **0/12** |
| history sentence, undated | 12/12 | 11/12 |
| Simulated AtticDB block: dated lines and header | 12/12 | 12/12 |

- The same stale rule agents followed 12/12 times from `CLAUDE.md`, they set aside 12/12 times from a memory block. They cited the refactor commit's message.
- The history miss is the case dates exist for: "I couldn't tell which of the two was written more recently. The convention note has no date."

## 3. Rule from a memory hook, refactor commits name only files, 2 reps

The refactor commit says only "Update app/books.py and tests/test_books.py". Now dates are the only clue.

| Arm | Stale | Migration | Ran git |
|---|---|---|---|
| plain, undated | **0/8** | 8/8 | 2/16 |
| history sentence, undated | 3/8 | 8/8 | 15/16 |
| Simulated AtticDB block | **0/8** | 8/8 | 2/16 |
| dated + anchor + sentence in the user's CLAUDE.md | 8/8 | 8/8 | 14/16 |
| dated + sentence in the user's CLAUDE.md, no anchor | **8/8** | **8/8** | 16/16 |
| dated + anchor, no sentence | 7/8 | 3/8 | 6/16 |
| dated + sentence in AtticDB's header | 6/8 | 8/8 | 12/16 |

- The simulated AtticDB block failed every vague stale case.
- Dates are needed. Undated, the sentence gets 3/8.
- The sentence is needed. Dates alone, or a raw "N commits since", don't make agents compare. Without the sentence, "Since then, 0 commits changed app/" still pulled 5 of 8 migrations to the old code.
- The commit anchor isn't needed once the agent has the date and the sentence.
- The sentence in the user's `CLAUDE.md` beats the same sentence in the hook block: 8/8 vs 6/8. Both header misses never ran git. That matches the paper's account: an instruction outranks other context.

## 4. Shipped rule, 3 reps (2026-11-24)

Same fixtures as section 3: memory channel, commits name only files. Claude Code 2.1.310, `claude-sonnet-5-5`.
72 runs, 0 errors, $4.01 at API prices. CSV: [2026-11-24-dated-rule.csv](2026-11-24-dated-rule.csv).

| Arm | Stale | Migration | Ran git |
|---|---|---|---|
| `atticdb-today`: header as shipped in v0.3.3 | **0/12** | 12/12 | 4/24 |
| `atticdb-next`: header with the #233 rule | 11/12 | 12/12 | 21/24 |
| `atticdb-next-guide`: header and guide, both with the rule | **12/12** | **12/12** | 24/24 |

- The shipped header fails every vague stale case again. Agents rarely run git.
- The rule in the header fixes 11 of 12. Its 1 miss, `errors` stale rep 1, never ran git.
- The guide arm puts the same 3 sentences in the user `CLAUDE.md`, as `connect` writes them into the Copilot, Codex and Gemini guides. It got every case right.
- Claude Code gets the guide from the MCP server's instructions, not a user file. These runs have no MCP, so that path is untested.
- 3 reps, 4 conventions, 1 model. Not a claim about other agents or real repos.

## What this means

- The "existing code wins" fix trades stale-rule failures for migration failures. Neither is caught by tests.
- A save date and a history instruction in the user's `CLAUDE.md` got 16/16 right in the neutral-message fixtures.
- With the instruction in the simulated hook instead, 2 of 8 stale cases still failed.
- A save date helped in these fixtures. It does not establish whether a rule is correct or still applies.

## Limits

- 1 harness and 1 model. Neither Copilot CLI nor Codex was tested.
- The CSVs record the model ID, not the provider environment. They predate the runner's environment and grader fixes.
- 4 conventions, each with a clean 3-commit history. Real repos are messier.
- The AtticDB header names `memory_search` and `fact_get`, which these runs don't have.
- `plain` in the memory channel uses a short header. So it mixes 2 changes: the channel and the header.
- 2 to 3 reps per cell. The candidate header has 2 reps on vague histories and 1 on clear ones.

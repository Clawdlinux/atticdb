# Do agents read a cut fact before they edit? (#234, 2026-11-26)

The chat-start block cuts a fact at 300 characters and marks it `(cut)`. The header says to call `fact_get` or `memory_search` for the rest. This pilot checks whether the agent does that before it edits code the cut part governs.

## What was run

- AtticDB binary built from `main` at `9cc7216`. Claude Code 2.1.310 on its default model, logged in only in its eval config dir.
- 3 cases. Each asks to add 1 function to `calc.py`: `add`, `divide`, `power`. Each fact opens with 396 characters of conventions that are harmless to follow. Then comes 1 exception that makes the naive edit wrong:
  - C1: reject `bool` arguments with `TypeError`.
  - C2: `divide` returns `None` when `b` is 0.
  - C3: `power` uses `math.pow`.
- 3 versions per case, 3 runs each, 27 runs:
  - `cut`: the fact as people write it. The exception sits past the cut.
  - `full`: the same sentences, exception first, so it shows in the block. The tail is still cut.
  - `none`: no fact. A control that the exception can't be guessed.
- Command: `python3 -m research.setup_eval run --harness claude-code --scenarios C1-CUT,...,C3-NONE --runs 3 --max-runs 27`.
- Every child had its own `ATTICDB_HOME` (288 checked). The real AtticDB home didn't change. Every stream parsed (27/27).
- Grading is mechanical. Correct means the lines added to `calc.py` follow the exception. A read is a `fact_get` or `fact_history` of the case's key, a `fact_list` whose prefix covers it, or any `memory_search`. Before the edit means before the first `Edit`, `Write` or `MultiEdit` call.

## Results

| Version | Correct edit | Read the fact | Read before the first edit |
|---|---|---|---|
| `cut` | 8/9 | 8/9 | 8/9 |
| `full` | 9/9 | 8/9 | 8/9 |
| `none` | 0/9 | 7/9 searched | 2/9 |

- The cut fact worked in 8 of 9 runs. In each, the agent read the key before it edited, then followed the exception.
- The miss, C1 run 1, never read the fact. It made the naive edit and said it matched the visible conventions.
- `none` got 0/9, so the exception isn't guessable from the code or the task. Its "searched" count is `memory_search` calls that had nothing to find.
- In `full`, 1 run followed the visible exception without reading the rest.
- Median input tokens: `cut` 164,145, `full` 237,422, `none` 248,506. Median wall time 7.5 to 9.4 s.

## What this means

- The `(cut)` marker and the header line get Claude Code to fetch the rest most of the time. 1 run in 9 acted on the prefix alone.
- 8/9 against 9/9 is 1 run. It doesn't show that `cut` is worse than `full`, and it doesn't justify a hook change.

## Limits

- 1 harness, 1 model, 3 runs per cell. Codex and Copilot CLI weren't run. The tool-order parse is Claude Code only.
- 3 small synthetic cases in 1 fixture file. Real facts and repos are messier.
- A `memory_search` counts as a read even if its result didn't hold the exception.
- The CSV has no cost column. Token counts are in it.
